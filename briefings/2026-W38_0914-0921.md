## 🔍 1. AI Eval

### ① ImpossibleRubrics: Stress-Testing Generated Rubrics as Reward Signals ⭐⭐⭐
**2026-09-15** · https://arxiv.org/abs/2609.16816

LLM 생성 rubric이 rubric 기반 RL·LLM-as-judge의 보상 신호로 쓰일 때 얼마나 쉽게 악용되는지 스트레스 테스트. 근거 없는 결론을 강요하는 "불가능한 과제" 169개 + 대조군 48개로 벤치마크를 만들고, 각 과제에 **검증 가능한 oracle certificate**(정직한 답변이 주장해도 되는 것 / 안 되는 것)를 붙였다. 결과: rubric 생성기 11종이 기본 조건에서 **8~26% 악용**, 스트레스 조건에선 최강 생성기도 36%. 가장 반직관적인 건 **과제 맞춤 rubric을 쓴 11개 중 7개가 범용 rubric 하나(64%)보다 더 자주 뚫렸다**는 것.

> 💡 핵심 문장: *"문제는 rubric이 모호하다는 게 아니라, 엉뚱한 것에 대해 구체적이라는 것."* 맞춤 rubric의 세부 항목이 공격자에게 "어떤 주장을 날조하면 되는지" 알려주는 단서가 된다. LLM-as-judge 파이프라인 쓰면 필독.

### ② An Empirical Study of Harness Design for Coding Agents ⭐⭐⭐
**2026-09-17** · https://arxiv.org/abs/2609.20804

실행 루프를 고정한 경량 harness에서 **planning / action space / context management** 3개 컴포넌트만 변화시켜 비교. 모델 4종 × SWE-Bench Verified + Terminal-Bench 2.1에서 **176개 matched setting** 평가. 발견: (1) context 관리 이득의 대부분은 overflow 실패 방지에서 옴, (2) 규칙 기반 elision을 LLM 요약 앞에 두는 게 효율 최강이고, elide된 내용 복구 기능은 모델이 거의 안 써서 정확도 이득 0, (3) planning은 약한 모델엔 정확도 보조재 / 강한 모델엔 비용 절감재, (4) bash 숙련 모델은 bash-only 인터페이스로 훨씬 싸게 동등 성능.

> 💡 "에이전트 벤치마크 점수 = 모델 성능"이 아니라는 걸 컴포넌트 단위로 입증. 에이전트 eval 공정비교의 핵심 교란변수.

### ③ Benchmark Radar — 벤치마크를 위한 검색엔진
**arXiv v1 9/10 (HF Daily Papers 9/14 1위, 229 upvotes)** · https://benchmark-radar.org/ · https://arxiv.org/abs/2609.11115

AI 벤치마크 자체를 추적하는 living DB. 37개 소스에서 매일 수집, **1,283개 source record / 12,916개 수치 관측치**. 벤치마크 포화, 채택 추세, "점수 대비 실사용량 Pareto frontier" 뷰 제공. MIT, 매일 01:00 UTC 자동 갱신.

> 💡 새 eval 설계 전 "선행 벤치마크 조사"를 체계적으로 할 수 있는 첫 인프라.

### ④ PACT: 엔터프라이즈 AI는 압박 하에서 신뢰할 수 있나
**2026-09-16** · https://arxiv.org/abs/2609.18605

12개 규제 도메인 × 48개 멀티턴 시나리오. 각 항목이 "지켜야 할 규칙"과 "규칙을 위반하는 지름길"을 짝지어 놓고, 집요한 사용자·급한 관리자 등 압박을 가함. 22개 모델 결과: 최강 모델도 **6~10%에서 규칙 오적용**, **평범한 사용자 압박만으로 위반율 평균 65% 상승**.

> 💡 LLM-as-judge를 "채점"이 아니라 **"벤치마크 품질 감사"**에 쓴 설계가 배울 만함.

### ⑦ Sample Count Is Not Enough (test-time scaling 비용 보고)
**2026-09-16** · https://arxiv.org/abs/2609.19499

Test-time scaling을 "후보 개수 N"으로만 보고하는 관행 비판. N=8 고정하고 스케줄만 1×8 / 2×4 / 4×2 / 8×1로 나눴더니 A100에서 **8회 순차 호출이 1회 배치 대비 GPU 에너지 4.64~4.86배, P95 지연 5.77~6.12배**.

> 💡 "같은 N"이 같은 비용이 아니다. 평가 보고 기준에 생성 스케줄 + GPU 지표를 넣어야 한다는 지적.

## 📄 6. 논문 — 아키텍처 · 효율 · RL

### ㉕ DeepSeek-V4.1-Flash: KV Cache 압축의 한계 밀어붙이기 ⭐
**9/17** · https://arxiv.org/abs/2609.19969

552B 백본(총 763B) 멀티모달 MoE, 1M 컨텍스트. **Causal Encoder-Decoder(CED)** 구조로 20레이어 encoder + 20레이어 decoder를 두어 **prefill 시 8B, decode 시 16B만 활성**. CSA2의 레이어 간 KV 재사용 + FP4 양자화로 글로벌 KV 캐시를 **토큰당 890바이트(이전 세대의 1/4)**까지 축소. 45T 멀티모달 토큰 사전학습. **가중치 MIT**.

> 💡 prefill/decode 활성 파라미터를 분리한다는 설계가 포인트. "긴 입력·짧은 출력" 에이전트 서빙 경제학을 바꿈.

### ㉖ Rethinking Critic Learning in PPO: Value Flattening (SP³O)
**9/16** · https://arxiv.org/abs/2609.18708

PPO critic의 새 실패 모드 **"Value Flattening"** 규명 — 실제 state value는 급변하는데 critic 예측은 평평하게 유지되는 현상. 원인: critic loss에 내재된 암묵적 분산 페널티 + 시간적으로 상관된 상태들의 중복 gradient. 해법 **SP³O**: 응답당 시간적으로 충분히 떨어진 **소수의 상태에만 value supervision** 적용. Qwen3-Base에서 **응답당 단 3개 상태만 감독해도** 성능 향상.

> 💡 "critic을 더 많이 학습시킬수록 좋다"를 뒤집음. 감독 신호를 *희소하게* 주는 게 오히려 credit assignment를 살림.

### ㉗ Edge0: SSD에서 35B MoE 서빙하기 (Trained Routing Prediction)
**9/16** · https://arxiv.org/abs/2609.18063

35B MoE를 **단일 24GB 머신**에서 서빙. 핵심은 **"prerouter"** — 한 레이어 앞서 expert 라우팅을 예측해, 현재 레이어 계산이 끝나기 전에 SSD 읽기를 미리 시작(연산과 I/O 겹침). 4비트 양자화 + **recovery LoRA**로 품질 보상. **peak active memory 3GiB 이내에서 20 tok/s**, 5개 벤치마크에서 full-precision과 수 %p 이내. CC BY 4.0.

> 💡 MoE offloading의 병목이 대역폭이 아니라 *라우팅을 아는 타이밍*이라는 통찰. ⑱ colibri와 정확히 같은 문제를 논문 쪽에서 푼 것 — **세트로 읽으면 좋음**.

### ㉘ SpectralShift: Gated DeltaNet의 컨텍스트 확장 🎯 트랜스포머 대안
**9/13 (HF Daily Papers 9/17)** · https://arxiv.org/abs/2609.14320

**linear attention 모델(GDN 등)의 컨텍스트 확장**. 기존 continued pretraining이 어텐션 동역학의 **스펙트럼 특성**을 무시한다고 지적하고, 롱컨텍스트에 필요한 두 조건을 규명: (1) 목표 길이에 정렬된 충분히 넓은 **느린 스펙트럴 밴드**, (2) state clearing/context switching용 **빠르게 감쇠하는 모드의 보존**. alpha projection 초기화와 LR 스케일링을 조정해 decay 스펙트럼을 재형성.

> 💡 linear attention의 컨텍스트 확장은 RoPE 스케일링 처방이 안 통하는 별개 문제이고, 열쇠가 gate의 decay 스펙트럼이라는 진단. ⑲ llama.cpp의 GDN 정규화 버그와 같은 메커니즘을 반대편에서 본 셈.

### ㉙ When2Think: 난이도 인지 길이 제어
**9/17** · https://arxiv.org/abs/2609.19671

**사전 계산된 레퍼런스 통계(정확도 + 토큰 사용량)**를 기준으로 추론 깊이를 조절하는 post-training 프레임워크. verifier reward + 표준화된 advantage 조합이라 **학습된 reward model 없이** 최적화 가능. **AIME24에서 정확도 +10.0%p 동시에 토큰 −27.9%**.

> 💡 정확도와 토큰을 트레이드오프하지 않고 *둘 다* 개선. length penalty와 달리 난이도 사전통계를 앵커로 쓴 게 차이.

### ㉚ When EOS Tokens Disagree: Length Inflation in On-Policy Distillation
**9/17** · https://arxiv.org/abs/2609.20511

on-policy distillation에서 학생이 불필요하게 긴 응답을 내는 원인을 **"termination-token mismatch"**로 규명. stopping set이 같아도 base student와 post-trained teacher가 **서로 다른 EOS 토큰에 정지 확률을 배분**하면 길이 팽창 발생. **기능적으로 동등한 EOS 토큰들을 하나의 의미적 정지 행동으로 통합**하면 Qwen3/Llama/Gemma 셋 다에서 크게 완화.

> 💡 distillation 길이 폭주를 reward hacking 탓하기 전에 **토크나이저 레벨 EOS 불일치**부터 확인. 즉시 적용 가능한 체크리스트.
